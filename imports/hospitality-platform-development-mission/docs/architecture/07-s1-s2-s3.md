# 07 — S1 + S2 + S3 Implementation

## Event lifecycle

```
DRAFT → QUOTED → CONFIRMED → PREPARING → DISPATCHED → IN_PROGRESS → RETURNING → CLOSED
         ↘         ↘           ↘
                    CANCELLED (only from DRAFT / QUOTED / CONFIRMED / PREPARING)
```

- `DRAFT → QUOTED` happens when the first quotation is issued.
- `QUOTED → CONFIRMED` happens when a quotation is accepted.
- Frontend cannot write `status` directly; only `transitionEventStatus` / `cancelEvent` / quote commands.

## Pricing methods

| Method | Selling / cost total |
| --- | --- |
| FIXED | unit |
| PER_EVENT | unit × quantity |
| PER_GUEST | unit × guestCount × quantity |
| PER_UNIT | unit × quantity |
| PER_HOUR | unit × hours (quantity) |
| PER_DAY | unit × days (quantity) |
| MANUAL | unit × quantity |

All arithmetic is integer milli-OMR via `multiplyOMR` (BigInt, half away from zero).

## Snapshot contract

- Applying a package copies catalog/package values into `event_pricing_lines`.
- Issuing a quotation freezes lines + guest/schedule/customer snapshots.
- Changing catalog/package later does not rewrite issued quotations or accepted commercial baselines.
- Accepted quotation locks further pricing edits.

## Staff overlap

Active assignments use half-open ranges `[start − bufferBefore, end + bufferAfter)`.
Back-to-back assignments that only touch at the boundary are allowed.

## Equipment capacity

`sum(overlapping ACTIVE reservations) ≤ totalQuantity`.
Reservation is lock-then-sum-then-insert (serialized in the engine).
Cancelled events release reservations and cancel assignments transactionally.
