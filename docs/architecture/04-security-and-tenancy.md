# 04 — الأمن وتعدد المستأجرين

## المنظمات والعضوية

- `organizations` — منظمة (مكتب). `profiles` — هوية المستخدم (منفصلة عن العضوية).
- `organization_memberships` — الرابط الصريح بين `auth.users` والمنظمة، ويحمل الدور
  وحالة العضوية. مستخدم واحد قد يحمل عدة مسؤوليات (عدة عضوية/أدوار).

### الأدوار

`OWNER`, `MANAGER`, `SUPERVISOR`, `WAREHOUSE`, `ACCOUNTANT`.

- التهيئة التجارية (كتالوج/باقات): `OWNER`, `MANAGER` فقط.
- المستخدمون التشغيليون لا يرون تلقائياً المعلومات المالية الحساسة.

## المصادقة

Supabase Auth حصراً. **لا** مسار دخول تجريبي، **لا** كلمات مرور صلبة، **لا** مستخدمين
وهميين، **لا** fallback صامت للأدوار.

## RLS

كل جدول أعمال مفعّل بـ RLS، ويُشتق نطاق المنظمة من عضوية المستخدم **النشطة**
(دوال `is_org_member` / `has_org_role` / `can_manage_commercial` بتعريف أمني
`SECURITY DEFINER` مع `search_path` مثبّت).

### حدود الامتيازات

| العملية | السياسة |
| --- | --- |
| قراءة بيانات المنظمة | عضو نشط |
| كتابة الكتالوج/الباقات | `OWNER` / `MANAGER` |
| كتابة العملاء | `OWNER` / `MANAGER` / `SUPERVISOR` |
| إدارة العضويات | `OWNER` |
| إنشاء منظمة | عبر RPC `create_organization` (المستدعي يصبح OWNER) |
| التدقيق | إلحاق عبر `record_audit` فقط |

## لا تثق في المنظمة المرسلة من العميل

`organization_id` لا يُؤخذ أبداً من الواجهة كمصدر ثقة؛ يُتحقق منه خادمياً عبر RLS،
وبالنسبة للباقات عبر قيود مفتاح أجنبي مركّبة تمنع بنيوياً عبور المنظمات.

## التدقيق

`audit_events` — أساس تدقيق إلحاقي: منظمة، مستخدم، فعل، كيان، معرف، طابع زمني، بيانات
وصفية مقيدة (بدون إغراق بيانات حساسة).

## فحص الأمان قبل الإتمام

التعرض العام للجداول، تفعيل RLS، صحة السياسات، دوال `SECURITY DEFINER` و`search_path`،
المنح، توسيع الأدوار، عدم تسريب الأسرار، الوصول غير المصادق — كلها تُراجع (انظر
`supabase/tests/rls_isolation.test.sql`).
