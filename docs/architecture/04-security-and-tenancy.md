# 04 — الأمن وتعدد المستأجرين

## المنظمات والعضوية

- `organizations` — منظمة (مكتب). `profiles` — هوية المستخدم (منفصلة عن العضوية).
- `organization_memberships` — الرابط الصريح بين `auth.users` والمنظمة، ويحمل الدور
  وحالة العضوية. مستخدم واحد قد يحمل عدة مسؤوليات (عدة عضوية/أدوار).

### الأدوار

`OWNER`, `MANAGER`, `SUPERVISOR`, `WAREHOUSE`, `ACCOUNTANT`.

- التهيئة التجارية (كتالوج/باقات): `OWNER`, `MANAGER` فقط.
- المستخدمون التشغيليون لا يرون تلقائياً المعلومات المالية الحساسة.

### رؤية البيانات المالية الحساسة

| البيانات | OWNER | MANAGER | ACCOUNTANT | SUPERVISOR | WAREHOUSE |
| --- | --- | --- | --- | --- | --- |
| سعر البيع | ✅ | ✅ | ✅ | ✅ | ✅ |
| سعر التكلفة | ✅ | ✅ | ✅ | ❌ | ❌ |
| الملاحظات التجارية الداخلية | ✅ | ✅ | ✅ | ❌ | ❌ |
| التهيئة التجارية (كتابة) | ✅ | ✅ | ❌ | ❌ | ❌ |
| كتابة العملاء | ✅ | ✅ | ✅ | ✅ | ❌ |

التنفيذ: `catalog_items` جدول واحد، لكن سياسة `SELECT` عليه مقيّدة بأدوار قراءة
التكلفة (`can_read_cost` = OWNER/MANAGER/ACCOUNTANT). الأعضاء التشغيليون يقرؤون
الإسقاط غير الحساس `catalog_items_operational` (عرض SECURITY DEFINER يصفّي حسب
المنظمة ولا يعرض `cost_price` / `internal_notes`). هذا فصل عند حدود البيانات، وليس
مجرد إخفاء في الواجهة.

## المصادقة

Supabase Auth حصراً. **لا** مسار دخول تجريبي، **لا** كلمات مرور صلبة، **لا** مستخدمين
وهميين، **لا** fallback صامت للأدوار.

## RLS

كل جدول أعمال مفعّل بـ RLS، ويُشتق نطاق المنظمة من عضوية المستخدم **النشطة**
(دوال `is_org_member` / `has_org_role` / `can_manage_commercial` بتعريف أمني
`SECURITY DEFINER` مع `search_path` مثبّت).

### حدود الامتيازات

| العملية | السياسة |
| --- | --- |
| قراءة بيانات المنظمة (تشغيلية) | عضو نشط في منظمة نشطة |
| قراءة سعر التكلفة/الملاحظات | `OWNER` / `MANAGER` / `ACCOUNTANT` |
| كتابة الكتالوج/الباقات | `OWNER` / `MANAGER` (لا DELETE من العميل) |
| كتابة العملاء | `OWNER` / `MANAGER` / `SUPERVISOR` |
| إدارة العضويات | `OWNER` |
| إنشاء منظمة | عبر RPC `create_organization` (المستدعي يصبح OWNER) |
| التدقيق (قراءة) | `OWNER` / `MANAGER` فقط |
| التدقيق (إلحاق) | داخلي فقط عبر `record_audit` (غير قابل للاستدعاء من العميل) |

## المنظمة غير النشطة

`is_org_member` / `has_org_role` تشترط أن تكون المنظمة نشطة (`organizations.is_active`)
**بالإضافة** إلى العضوية النشطة. منظمة غير نشطة تمنع القراءة والكتابة المحميتين حتى لو
بقيت صفوف العضوية نشطة. الاستعادة تتم بإعادة تفعيل المنظمة (موثّق هنا، وليس عبر
منح قراءة جزئية).

## الحذف التدميري

بيانات الأعمال الرئيسية (كتالوج/تصنيفات/باقات) لا تُحذف من العميل؛ تُستخدم دلالات
`ACTIVE`/`INACTIVE` للتفعيل/التعطيل. لا توجد سياسات `DELETE` على هذه الجداول. استبدال
أسطر قالب الباقة يتم عبر `save_package()` المعاملاتي فقط.

## لا تثق في المنظمة المرسلة من العميل

`organization_id` لا يُؤخذ أبداً من الواجهة كمصدر ثقة؛ يُتحقق منه خادمياً عبر RLS،
وبالنسبة للباقات عبر قيود مفتاح أجنبي مركّبة تمنع بنيوياً عبور المنظمات.

## التدقيق

`audit_events` — أساس تدقيق إلحاقي: منظمة، مستخدم، فعل، كيان، معرف، طابع زمني، بيانات
وصفية مقيدة (بدون إغراق بيانات حساسة). `record_audit` **داخلي فقط** (مُسحَب منه
`EXECUTE` من `authenticated`/`anon`) ويُستدعى من الأوامر المعتمدة (مثل
`save_package`)، فيشتق هوية المستدعي خادمياً ولا يسمح بتمرير منظمة عشوائية من العميل.

## فحص الأمان قبل الإتمام

التعرض العام للجداول، تفعيل RLS، صحة السياسات، دوال `SECURITY DEFINER` و`search_path`،
المنح، توسيع الأدوار، عدم تسريب الأسرار، الوصول غير المصادق — كلها تُراجع (انظر
`supabase/tests/rls_isolation.test.sql`).
