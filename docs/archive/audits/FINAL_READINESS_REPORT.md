## 1. ما نُفِّذ بالكامل (A–E)

### Phase A — الهوية والمستندات
- إعدادات المنشأة (هوية/تواصل/قانوني/ترقيم/توقيع) — لا شيء hard-coded.
- محرك مستندات موحّد `DocumentShell` + طباعة/PDF عربي RTL.

### Phase B — المحرك التجاري
- مكوّنات السعر: `subtotal + transport + surcharge − discount = grand total` بمصدر SQL واحد.
- دورة حياة العرض (REJECTED/EXPIRED/CANCELLED/SUPERSEDED) + نسخ (Revision) لا يمحو التاريخ.
- ترقيم مستندات من الإعدادات. نطاق ضيوف الباقات كتوصية فقط.

### Phase C — التشغيل
- مركز قيادة المناسبة + Readiness قابل للتفسير (مطلوب/مخصص) + خط زمني.
- بوابة جاهزية على الإرسال مع override مُدقَّق. تقويم + لوحة تشغيل يومية.

### Phase D — المالية
- مصروفات موحدة (VOID، لا تضاعف مشتريات/عمالة) + ربحية فعلية (Revenue ≠ Collected ≠ Profit).
- إغلاق مالي كـ«حدث أعمال»: دورة تاريخية مع لقطة مالية + حارس منع التعديل بعد الإغلاق.

### Phase E — الذكاء الإداري
- لوحة إدارة + قائمة انتباه + تنبيهات ذكية (server-side) + Customer 360 + بحث شامل + مركز سلامة + تقارير.
- كل رقم قابل للتفسير والتوجيه إلى سجله المصدر، ومنعزل بالمنظمة، ومُصان بالأدوار.

## 2. مراجعة التدفق الكامل (E20)

**التحقق من التدفق:** عميل → عرض → نسخة → اعتماد → مناسبة → تجهيز → موارد →
تنفيذ → تحصيل → مصروفات → إغلاق تشغيلي → إغلاق مالي → ربحية → ذكاء إداري.

كل خطوة مترابطة وتُستهلك من الخطوة السابقة دون إعادة إدخال. **لم يُكتشف أي فجوة
حاسمة تكسر التدفق.** ملاحظات التكامل المعروفة (مقبولة عمداً):

| # | الملاحظة | القرار |
| --- | --- | --- |
| G1 | `report_packages` يعدّ «القيمة التجارية» لكل عرض استخدم الباقة، لكن «الربح» يُحسب فقط للمناسبات المحوّلة (لأن الربح مصدره المناسبة المالية) | مقبول — يُفصل بوضوح: قيمة العروض مقابل ربح المناسبات المنفَّذة |
| G2 | القيمة المتوسطة للعرض تشمل العروض الصادرة/المعتمدة/المحوّلة فقط (لا المسودات) | مقصود |
| G3 | لا مرفقات/ملفات (طلب Phase E المبكر لم يتضمنها؛ عُدّلت لاحقاً نحو العمق التشغيلي) | مؤجَّل — خارج نطاق A–E |

## 4. متطلبات النشر الإنتاجي (قبل الاستخدام الفعلي)

1. **مشروع Supabase إنتاجي** + تطبيق الترحيلات الـ 69 (من قاعدة فارغة).
2. **نطاق Vercel** + متغيرا `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`.
3. **قرار التسجيل الذاتي** (`enable_signup`) وسياسة إنشاء المنظمات.
4. **تجهيز حساب الإنتاج**: إنشاء منظمة «مشاريع جودة الإنطلاقة»، حساب المالك،
   وإدخال الكتالوج والباقات الأربع كبيانات (وليس ثوابت كود).
5. **نسخ احتياطي مجدول** على مشروع Supabase.
6. **معاينة المستخدم النهائي (UAT)** مرة واحدة على بيانات حقيقية صغيرة.

> لا توجد أسرار أو اعتماديات في المستودع؛ كل التهيئة عبر بيئة الاستضافة.

## 5. حدود اختبار المتصفح (E2E)

- **لا يوجد harness E2E على مستوى المتصفح** في هذا المستودع (لا Playwright ولا
  Cypress مفعّلان؛ بيئة العمل لا توفر متصفحاً لتشغيله والتحقق منه).
- التغطية الحالية: **pgTAP** (ثوابت قاعدة البيانات وRLS وcommands — 21 ملفاً)،
  **unit tests** (منطق المجال)، **component/integration tests** (سلوك الواجهة) —
  578 اختباراً / 81 ملفاً.
- **الفجوة المتبقية** (مسجَّلة بدقة، وليست مسمّاة خطأً بـ E2E): رحلة مستخدم
  حقيقية عبر متصفح على بيئة إنتاج حقيقية. تُسدّ بـ UAT بشري أو بإضافة Playwright لاحقاً.

## 6. الحكم النهائي

**هل التطبيق جاهز للاستخدام اليومي الحقيقي في المكتب؟**

- **هندسياً وأمنياً ووظيفياً: نعم.** النظام متكامل الدورة (من الاستفسار إلى الربح
  الفعلي)، بذاكرة تاريخية، يمنع الحالات غير الصالحة، يشرح ما هو خطأ، يبرز ما يحتاج
  انتباهاً، ويربط الحقيقة التشغيلية بالمالية. كل بوابات الجودة خضراء وكل المال
  بدقة `numeric(12,3)` مع عزل منظمات إلزامي.
- **تشغيلياً (إطلاق فعلي): يلزمه خطوات §4** — تجهيز بيئة إنتاج + بيانات افتتاحية +
  معاينة بشرية واحدة. هذه خطوات مالك/مشغّل، وليست عيوباً في المنتج.

**الخلاصة:** المنتج **جاهز للاستخدام** من حيث الجوهر؛ خطوة الإطلاق الفعلي هي تجهيز
البيئة والبيانات وليست إعادة بناء. لا يُنصح بأي توسّع ERP إضافي قبل تشغيله فعلياً
وجمع ملاحظات الاستخدام الأولى.
